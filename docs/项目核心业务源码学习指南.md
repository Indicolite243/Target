## 1. 项目总体定位和技术架构

这是一个面向量化投研、私募基金账户管理和 QMT 交易执行的股票决策可视化系统。系统覆盖：

- 用户注册、登录和权限认证；
- QMT 账户资产和持仓同步；
- 实时行情和五档盘口展示；
- 手动下单、撤单、成交状态同步和订单历史管理；
- SuperMind/MindGo 风格策略回测；
- 组合风险评估；
- 资产配置、区间收益对比和收益归因；
- 异步任务、幂等、审计、状态历史和故障恢复。

### 1.1 总体调用关系

```text
Vue 3 前端
   │ Axios：JWT、TraceId、RequestId
   ▼
Spring Boot 主后端
   ├── Controller：HTTP 接口、参数绑定
   ├── Service：业务编排、事务边界、权限校验
   ├── MyBatis-Plus：数据库访问
   ├── MySQL：用户、账户、订单、历史快照、分析结果
   ├── Redis：实时缓存、分布式锁、JWT 黑名单
   └── QuantClient：调用量化服务
                  │ 内部Token、TraceId、超时和错误映射
                  ▼
           FastAPI 量化服务
             ├── xtquant/MiniQMT：行情、账户、下单、撤单
             ├── MindGo/SuperMind 兼容回测引擎
             └── NumPy：风险和组合计算
```

### 2.4 注册业务的额外步骤

注册不仅插入用户，还会创建模拟交易账户：

```text
AuthController.register()
   ▼
AuthServiceImpl.register()
   ├── 校验两次密码一致
   ├── BCrypt 加密密码
   ├── 插入 sys_user
   └── AccountProvisioningService.createSimulationAccount()
          ├── 创建 account
          └── 创建初始 position
```

注册方法使用 `@Transactional`。用户和模拟账户必须一起成功，否则整体回滚。

### 2.5 登出和 Token 黑名单

```text
POST /api/v1/auth/logout
   ▼
解析 JWT 的 jti 和 expiration
   ▼
Redis：stock:auth:blacklist:{jti}
   ▼
TTL = Token 剩余有效时间
```

Redis 这里只保存已撤销 Token，不保存用户主数据。

### 2.6 面试要点

- JWT 是无状态认证，服务端不需要保存登录 Session；
- Redis 黑名单解决“JWT 已签发但用户主动退出”的问题；
- 密码数据库中保存的是 BCrypt 密文，不保存明文；
- 所有业务接口默认要求认证，登录、注册、健康检查和 OpenAPI 文档放行；
- 退出登录后，前端清理 Token，后端通过 jti 黑名单拒绝后续请求。

### 3.5 定时采集和历史快照

[PortfolioLiveScheduler.java](D:/Target/backend/src/main/java/com/stockmanager/account/live/PortfolioLiveScheduler.java)：

- QMT 账户采集大约每 2 秒执行；
- Redis 快照写入 MySQL 当前表大约每 30 秒执行。

[PortfolioHistoryScheduler.java](D:/Target/backend/src/main/java/com/stockmanager/account/history/PortfolioHistoryScheduler.java)：

- 交易时段每 5 分钟采集历史快照；
- 每日收盘后保存日终快照；
- 使用本地锁避免同一个进程重复执行。

历史数据会根据数据版本、时间和持仓指纹去重，避免每次行情轮询都产生一条重复历史记录。

### 3.6 Redis 和 MySQL 的职责

```text
Redis
 └── 高频读取、实时展示、短 TTL 缓存、分布式锁

MySQL account/position
 └── 当前稳定状态

MySQL account_snapshot/position_snapshot
 └── 不可变历史数据、风险分析和收益曲线
```

### 3.7 并发控制

实时刷新有两层锁：

```text
同一JVM内：ReentrantLock
多实例部署：Redis token lock
```

Redis 锁释放通过 Lua 脚本比较 token，只有持有锁的线程才能删除锁，避免线程 A 误删线程 B 的锁。

### 3.8 注意兼容路径

`AccountServiceImpl.syncAccountInternal()` 是较早的完整同步路径，保留用于兼容；当前手动刷新主要经过 `PortfolioLiveService.refresh()`。阅读源码时要区分这两个入口，避免误以为存在两套互相冲突的实时逻辑。

### 5.4 订单状态机

```text
PENDING_SUBMIT
      │
      ├── QMT接受 → SUBMITTED
      ├── 业务拒绝 → REJECTED
      └── 网络/服务异常 → UNKNOWN

SUBMITTED
      │
      ├── 部分成交 → PARTIALLY_FILLED
      ├── 完全成交 → FILLED
      └── 发起撤单 → CANCEL_PENDING → CANCELED
```

可撤状态：

```text
SUBMITTED、PARTIALLY_FILLED、UNKNOWN
```

不可撤状态：

```text
FILLED、CANCELED、REJECTED、FAILED
```

### 5.5 为什么需要订单状态调度器

下单接口返回成功只代表 QMT 接受了委托请求，不代表已经成交：

```text
系统提交订单
   ▼
QMT返回外部订单号
   ▼
系统状态 SUBMITTED
   ▼
OrderStatusScheduler 每3秒查询QMT
   ▼
得到最新成交数量和撤单状态
   ▼
更新 MySQL 状态历史
```

[OrderStatusScheduler.java](D:/Target/backend/src/main/java/com/stockmanager/trade/order/scheduler/OrderStatusScheduler.java) 会批量查询未完成订单，并根据外部订单号匹配 QMT 返回结果。

### 5.6 撤单链路

```text
OrderList.vue 点击撤单
   ▼
POST /orders/{orderId}/cancel
   ▼
OrderServiceImpl.cancel()
   ├── 事务更新 CANCEL_PENDING
   ├── QuantClient.cancelOrder()
   ├── FastAPI 调用 cancel_order_stock()
   └── 后续由调度器确认最终 CANCELED
```

QMT 返回“撤单请求已接受”时，系统不能立即认定撤单完成，仍需查询 QMT 的最终状态。

### 5.7 订单查询、日期范围和删除

订单查询直接使用 MySQL，不需要新增数据库：

```sql
WHERE account_id = ?
  AND deleted_at IS NULL
  AND created_at >= ?
  AND created_at < ?
```

结束日期按“次日零点，右开区间”处理，避免当天 23:59:59 的边界问题。

删除采用软删除：

```text
trade_order.deleted_at = 当前时间
```

删除只隐藏本系统历史展示，不会删除：

- QMT 侧真实委托；
- `trade_order_status_history` 状态历史；
- `trade_order_audit` 审计日志。

## 9. 统一异步任务系统

回测、风险评估和收益归因都是长耗时业务，统一通过 `quant_task` 执行。

### 9.1 任务状态链路

```text
创建任务
   ▼
PENDING
   ▼
线程池抢占并 CAS 更新
   ▼
RUNNING
   ├── 成功 → SUCCEEDED
   ├── 失败 → FAILED
   └── 用户取消 → CANCELLED
```

核心文件：

- [QuantTaskService.java](D:/Target/backend/src/main/java/com/stockmanager/quanttask/service/QuantTaskService.java)
- [QuantTaskController.java](D:/Target/backend/src/main/java/com/stockmanager/quanttask/controller/QuantTaskController.java)
- [QuantTaskExecutorConfig.java](D:/Target/backend/src/main/java/com/stockmanager/quanttask/config/QuantTaskExecutorConfig.java)
- [QuantTaskResultService.java](D:/Target/backend/src/main/java/com/stockmanager/quanttask/service/QuantTaskResultService.java)

### 9.2 为什么使用异步任务

如果回测同步执行，HTTP连接会长期阻塞，容易超时并占满请求线程。现在的方式是：

```text
创建任务立即返回 taskId
   ▼
前端查询任务状态
   ▼
后台线程继续执行
   ▼
任务成功后读取结果
```

线程池和请求线程隔离，避免回测影响普通登录、行情和订单接口。

### 9.3 幂等和恢复

订单和任务都使用幂等键，数据库唯一约束保证重复提交不会创建重复记录：

```text
user_id + idempotency_key
user_id + task_type + idempotency_key
```

任务状态更新采用条件更新：

```sql
UPDATE quant_task
SET status = 'RUNNING'
WHERE id = ?
  AND status = 'PENDING'
```

应用重启后，未完成任务会被标记为中断失败，不会在没有明确策略的情况下自动重复执行可能产生副作用的任务。

## 10. 事务、锁和一致性设计

### 10.1 适合放在数据库事务中的操作

- 创建订单、状态历史和审计日志；
- 更新订单状态、状态历史和审计日志；
- 注册用户和创建模拟账户；
- 更新账户并替换当前持仓；
- 保存风险评估结果；
- 保存回测和归因结果。

### 10.2 不应长时间放在事务中的操作

- 调用 QMT；
- 调用 FastAPI；
- 执行回测；
- 等待网络接口返回。

订单采用“两段事务”：

```text
事务1：创建 PENDING_SUBMIT
   ▼
事务外：调用QMT
   ▼
事务2：更新 SUBMITTED、REJECTED 或 UNKNOWN
```

这样不会因为 QMT 响应慢而长期占用数据库连接。

### 10.3 最终一致性

订单系统不是提交接口和券商状态之间的强一致，而是最终一致：

```text
系统提交成功 ≠ 券商已经成交
```

必须依靠后续 QMT 查询确认最终成交数量、成交价格和撤单状态。因此系统保存：

- 当前订单状态；
- 状态变更历史；
- 审计日志；
- QMT 外部订单号。

## 13. 面试时的一句话项目介绍

> 这是一个面向量化投研和私募交易场景的股票决策可视化系统。前端使用 Vue 展示账户、行情、订单、回测和风险分析；Spring Boot 负责认证、权限、订单状态机、任务调度和数据持久化；FastAPI 负责连接 QMT 和执行量化计算；Redis 用于实时数据缓存、分布式锁和 JWT 黑名单；MySQL 保存交易、资产快照和分析结果，最终形成从行情采集、策略回测、风险评估到真实交易执行的完整闭环。

## 14. 与黑马点评项目的区别

黑马点评重点是高并发优惠券、秒杀、抢购和社交点评；本项目重点是：

- 金融账户和持仓的时序数据；
- QMT 外部交易接口；
- 真实订单生命周期和撤单状态机；
- 策略回测和 SuperMind/MindGo 兼容；
- 风险指标、资产配置和收益归因；
- Redis 实时快照与 MySQL 历史快照分层；
- 外部系统调用下的最终一致性、幂等和审计。

因此两者都可以讨论 Redis、事务、并发和幂等，但业务目标不同：黑马点评解决的是互联网高并发交易活动，本项目解决的是量化投研、组合管理和券商交易闭环。
